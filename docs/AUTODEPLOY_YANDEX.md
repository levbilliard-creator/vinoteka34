# Автоматическая публикация VINOTEKA34

Подготовлено 14.11.2026. Подключение к настоящему бакету и первый запуск пока не выполнены.

## Как это работает

После изменения рабочих файлов в main GitHub Actions проверяет код и каталог, сравнивает содержимое с бакетом vinoteka34.ru, сохраняет предыдущие файлы как rollback-артефакт на 30 дней, затем загружает измененные файлы и сверяет их содержимое. Отдельно предусмотрен ручной запуск. Параллельные публикации не выполняются. При штатно обработанной ошибке загрузки скрипт пытается восстановить прежние файлы; при аварийной остановке runner или недоступности сети может понадобиться ручной откат из артефакта.

Новые файлы при откате не удаляются. Записи, отсутствующие в репозитории, публикация не удаляет. Объекты data/inventory.json, README, служебные скрипты, ключи и резервные архивы на публичный сайт не загружаются.

Этот процесс публикует сайт, но не выполняет импорт учетных выгрузок, проверку названий или изменение цен. Текущие тесты фиксируют согласованные 553 позиции; при осознанном обновлении ассортимента ожидаемые количества нужно пересмотреть вместе с данными.

## Разовая настройка

1. В Яндекс Облаке, в существующей папке default облака vinoteka34-site, создать сервисный аккаунт vinoteka34-deploy без ролей на весь каталог/облако.
2. У существующего бакета vinoteka34.ru открыть права доступа и выдать этому аккаунту роль storage.uploader только на этот бакет. Эта роль разрешает чтение и запись объектов, но не удаление и не настройку бакета. Если интерфейс предлагает права на всю папку, остановиться и выбрать назначение на конкретный бакет.
3. У сервисного аккаунта создать статический ключ доступа. Две части ключа вводятся непосредственно в GitHub, а не в переписку и не в файлы репозитория. Экран с секретом не отправлять скриншотом.
4. В репозитории levbilliard-creator/vinoteka34 открыть Settings → Environments → создать production. Добавить environment secrets YC_ACCESS_KEY_ID и YC_SECRET_ACCESS_KEY. Для этого окружения разрешить публикации только из main. При поддержке текущим тарифом можно настроить подтверждение выпусков в самом GitHub; без него каждый push в main публикуется автоматически.
5. Внести подготовленные изменения из fix/catalog-stability-2026-11-14 в main. Первый запуск начнется после появления workflow в main и наличия обоих секретов. Предварительно проверить настройки доступа к публикации и бакет. Если секреты еще не добавлены, workflow остановится до подключения к хранилищу.
6. В Actions открыть Publish VINOTEKA34 to Yandex. Проверить первый запуск и домен vinoteka34.ru. Секреты и разрешения не создаются самим workflow.

## Ограничения и диагностика

В консоли на скриншоте также виден Cloud CDN. Скрипт проверяет байты непосредственно в Object Storage. CDN может показывать предыдущую версию до обновления его кэша. Первую публикацию нужно проверить на домене; при необходимости отдельно настроить очистку конкретного CDN-ресурса. Доступ к CDN в ключ загрузки не включен.

Загрузка статических файлов по отдельности не является атомарным переключением версии. HTML загружается после зависимостей, index.html последним. Не обещать отсутствие переходного состояния во время публикации. При ошибке сайт проверяется до повторного запуска.

Для ручного отката скачать rollback-артефакт соответствующего запуска Actions, распаковать его в .deploy-work в том же checkout и выполнить python3 scripts/deploy_yandex.py rollback с ключами в окружении. Архив содержит plan.json и rollback.zip. Скрипт восстанавливает существовавшие ранее объекты; новые остаются. Для отката на GitHub можно также подготовить проверенный возврат исходников в main и выпустить его обычным процессом.

## Проверки

- node --test tests/catalog.test.cjs: шесть тестов каталога.
- python3 -m unittest discover -s tests -p '*_test.py': четыре теста публикации с тестовым S3-клиентом.
- Публикация в настоящий бакет пока не проверена: требуется разовая выдача доступа и сохранение ключей.
